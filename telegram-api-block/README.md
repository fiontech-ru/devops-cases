# Кейс: обход блокировки api.telegram.org

Форма обратной связи возвращала `200 OK`, но уведомления в Telegram
не приходили. Диагностика выявила сетевую недоступность
`api.telegram.org` (ни IPv4, ни IPv6). Решение — локальный прокси
`tgwsapiproxy` через Cloudflare Worker.

## Проблема

Эндпоинт `POST /api/v1/feedback` возвращал `200 OK`, но уведомления в Telegram не приходили.

**Как обнаружили:** поддержка (L1) получила жалобы пользователей,
воспроизвела симптом (форма отправляется, ответа нет) и завела
TICKET-1. Доступа к логам и очереди у L1 нет — причину локализовать
не смогла, эскалировала разработчику.

## Разбор по ролям

- **Разработчик (TICKET-2)** проверил бэкенд: задача встаёт в очередь,
  но job падает с таймаутом ~30 с. Код в порядке — эскалация
  в инфраструктуру (TICKET-3).
- **DevOps (TICKET-3):** `curl` с хоста и из контейнера — соединения
  к `api.telegram.org` нет ни по IPv4 (таймаут), ни по IPv6
  (`Network is unreachable`). При этом `google.com` доступен —
  ограничение именно в доступности Telegram, не в сети сервера.

Подробная диагностика с командами и выводами — в
[diagnosis.md](./diagnosis.md).

## Решение

Цепочка:
laravel-worker → tgwsapiproxy (локальный прокси) → Cloudflare Worker → api.telegram.org

- **DevOps (L3):** развернул Cloudflare Worker, собрал контейнер
  `tgwsapiproxy`, подключил его к сети `app-blog-network`, вынес
  параметры в `.env`. Прокси ограничен `api.telegram.org` —
  не открытый релей.
- **Разработчик (L2):** добавил в `AbstractTelegramService` метод
  `http()` с `proxy` и `force_ip_resolve => 'v4'`, заменил `Http::`
  на `$this->http()` в `V1`/`V2`, добавил `retry` с callback
  на `ConnectionException`.

Подробности — в [solution.md](./solution.md).

## Результат

- Уведомления из формы обратной связи доставляются в Telegram.
- Job `SendTelegramMessage` больше не падает по таймауту:
  в логах воркера — `DONE` вместо `FAIL`.
- Приложение работает с прокси и без — переключение через
  `TELEGRAM_PROXY_URL`, без изменения кода.
- Ретраи ограничены сетевыми ошибками, 4xx не повторяются.

## Что бы я сделал иначе

- **Runbook заранее:** если бы был документ «что делать, если
  Telegram не доставляет», диагностика заняла бы часы, а не дни.
- **Мониторинг:** алерт на падение `SendTelegramMessage` выявил бы
  проблему до жалоб пользователей.
- **Разделение задач:** DNS-проблема с `mysql-dev` (обнаружена
  при диагностике) — отдельный инцидент, его можно было решать
  параллельно.
